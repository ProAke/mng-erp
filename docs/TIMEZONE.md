# วัน เวลา และการลงเวลา Asia/Bangkok

ระบบ Vanilla JS SPA และ Express ใช้ **Asia/Bangkok (UTC+07:00)** สำหรับวันและเวลาที่คนไทยเห็น ไม่ขึ้นกับ timezone ที่ตั้งในเบราว์เซอร์ การตั้ง timezone ไม่ใช่การปรับนาฬิกาที่เดินผิด: ผู้ดูแลต้องดูแลให้ **นาฬิกาของเครื่อง Express และเครื่อง MariaDB ตรงเวลาจริง** โดยใช้ NTP หรือบริการเทียบเวลาอื่นที่องค์กรเชื่อถือ

## ปฏิทิน

- วันที่ `YYYY-MM-DD` เป็น **วันที่ตามปฏิทินไทย** และเวลา `HH:mm` เป็นเวลาไทย เช่น `2027-01-01` + `00:00` คือเที่ยงคืนเมื่อเริ่มวันที่ 1 มกราคมในกรุงเทพ ไม่ต้องนำวันที่ล้วนไปแปลงเป็น UTC แล้วเปลี่ยนวัน
- นัดหมายแบบระบุเวลาต้องเริ่มและสิ้นสุดในวันเดียวกัน โดยเวลาสิ้นสุดต้องหลังเวลาเริ่ม เวลา `00:00` เป็นเวลานัดจริง ไม่ใช่เครื่องหมายตลอดวัน ให้ใช้ `allday: true` สำหรับกิจกรรมตลอดวันเท่านั้น API ตอบ `400 invalid_event_datetime` เมื่อวันหรือช่วงเวลาไม่ถูกต้อง
- มุมมองเดือนเริ่มวันจันทร์ มุมมองสัปดาห์/วันมีครบ 24 ชั่วโมง แสดงเส้นเวลาปัจจุบันและรายการตลอดวันแยกจากนัดที่ระบุเวลา บนมือถือเปิด **ตัวกรอง** เพื่อดูปฏิทินย่อยและหมวด และเลื่อนตารางสัปดาห์ในแนวนอนได้
- ปุ่ม **วันนี้** และวันเริ่มต้นอ้างอิงวันกรุงเทพ เมื่อเปิดหน้าค้างข้ามเที่ยงคืน วันจะอัปเดตเมื่อหน้าแอปมองเห็นและกำลังดูวันนี้อยู่ ส่วนวันที่อื่นที่เลือกเองจะไม่ถูกบังคับเปลี่ยน

## ลงเวลา

- ในโหมดฐานข้อมูล ปุ่มเช็กอิน/ออกส่งคำขอโดยไม่ส่งเวลาอุปกรณ์ เซิร์ฟเวอร์สร้างวันและเวลาจาก instant เดียวของตัวเอง แล้วบันทึกเป็นวันและเวลาไทย กดเช็กอินซ้ำขณะที่รอบยังเปิดจะรักษาเวลาเข้าเดิมและเปลี่ยนรูปแบบได้ กดออกซ้ำไม่ทับเวลาเดิม และกลับมาเช็กอินรอบใหม่ในวันเดียวกันได้
- API เดิมยังรองรับ `date` และ `time` ที่ผู้เรียกกำหนดเองสำหรับการบันทึกโดยตรง ค่าที่ส่งต้องเป็นวัน/เวลาไทยและผ่านการตรวจรูปแบบ แต่ **ไม่ใช่เวลาที่เซิร์ฟเวอร์ยืนยันว่าเกิดขึ้นจริง** หากต้องการเวลาปัจจุบันจากเซิร์ฟเวอร์ให้ละสองฟิลด์นี้
- การลงเวลาแยกตามวัน **ยังไม่รองรับเวลาออกของกะข้ามเที่ยงคืน** หากพบรอบก่อนหน้าที่ยังเปิด หน้าลงเวลาจะแจ้งให้ติดต่อผู้ดูแล และจะไม่ลงเวลาออกของวันใหม่ทับรอบเก่า ใช้วิธีบันทึกกะข้ามวันตามขั้นตอนขององค์กร
- ถ้าเริ่มต้นเทียบเวลาเซิร์ฟเวอร์ไม่ได้ อ่านข้อมูลลงเวลาไม่ได้ หรือโหลดข้อมูลใหม่หลังบันทึกไม่สำเร็จ หน้าลงเวลาจะแจ้งและไม่แสดงจำนวนเป็นศูนย์หรือเปิดปุ่มลงเวลาเสมือนข้อมูลพร้อม กด **ลองเชื่อมต่ออีกครั้ง** หลังตรวจการเชื่อมต่อ
- Bootstrap ระบุ `attendanceDate` เป็นวันกรุงเทพที่ใช้ดึงเช็กอินครบทั้งวัน พร้อมสถานะ `featureAvailability.attendance` หน้าลงเวลาและแดชบอร์ดจะไม่สรุปยอดจาก cache วันเก่าเมื่อข้ามเที่ยงคืน และจะพยายามโหลดข้อมูลใหม่เมื่อกลับเข้าหน้า หากโหลดไม่ได้ให้ลองเชื่อมต่ออีกครั้ง
- Bootstrap ดึงรายการของวันนี้ทั้งหมด ประวัติวันอื่นล่าสุดไม่เกิน 90 รายการ และรอบค้างก่อนหน้าของผู้ใช้อีกหนึ่งรายการหากมี สถิติวันติดของข้อมูลจริงจึงแสดงเป็น **อย่างน้อย** ตามประวัติที่โหลด ไม่ใช่รายงานประวัติ HR ทั้งหมด
- โหมดสาธิต/ออฟไลน์เก็บในเบราว์เซอร์และแปลงนาฬิกาอุปกรณ์เป็นเวลาไทย หากนาฬิกาอุปกรณ์ผิด เวลาสาธิตก็ผิด และข้อมูลไม่ถูกแชร์กับทีม ไม่ควรใช้เป็นหลักฐานลงเวลาจริง

## ตรวจนาฬิกาและการเชื่อมต่อ

1. ตรวจ `GET /api/clock` ของเซิร์ฟเวอร์ ERP ที่ใช้งานจริง (ไม่ต้องล็อกอิน; response ไม่ถูก cache) เช่น หลังตั้ง `MNG_ERP_URL` เป็น URL ระบบ:

   ```bash
   curl -fsS "$MNG_ERP_URL/api/clock"
   ```

   ตัวอย่าง response: `{"timezone":"Asia/Bangkok","serverTime":"2026-12-31T17:00:00.000Z"}` โดย `serverTime` เป็น **UTC instant ที่มี `Z`** ซึ่งตรงกับวันที่ 1 มกราคม 2027 เวลา 00:00:00 ในกรุงเทพ เปรียบเทียบ instant กับแหล่งเวลาที่เชื่อถือได้ ไม่ใช่บวกเจ็ดชั่วโมงให้ `Z` ซ้ำ
2. เมื่อเชื่อมฐานข้อมูล เบราว์เซอร์ใช้ endpoint นี้สอบเทียบนาฬิกากับเซิร์ฟเวอร์ตอนเริ่ม/เข้าสู่ระบบ และตรวจซ้ำขณะเปิดหน้า หากสอบเทียบครั้งแรกไม่สำเร็จ ปฏิทินจะแจ้งว่าแสดงจากอุปกรณ์ ส่วนหน้าลงเวลาจะให้ลองเชื่อมต่อก่อน ถ้าขัดข้องหลังเคยเทียบสำเร็จจะใช้ค่าเทียบล่าสุดต่อไป จนกว่าจะเทียบได้อีกครั้ง จึงควรตรวจการเชื่อมต่อและเวลาอุปกรณ์หากค้างออฟไลน์นาน
3. ตรวจ NTP/นาฬิกาของเครื่อง Express และ MariaDB แยกกัน เช่น `timedatectl status` บนระบบที่รองรับ `/api/clock` ไม่ใช่แหล่งเวลาอิสระ และการตั้ง timezone `+07:00` ไม่ซ่อมนาฬิกาของเครื่องที่เดินผิด
4. แอปตั้ง `time_zone = '+07:00'` **เฉพาะ session ของแต่ละ connection** ในทั้งสอง pool ไม่เปลี่ยนค่า GLOBAL ของ MariaDB หากต้องตรวจจาก SQL client แยก ให้ตั้งเฉพาะ session ทดสอบของ client แล้วเปรียบเทียบกับเวลาจริง:

   ```sql
   SET SESSION time_zone = '+07:00';
   SELECT NOW() AS bangkok_time, UTC_TIMESTAMP() AS utc_time,
          TIMESTAMPDIFF(SECOND, UTC_TIMESTAMP(), NOW()) AS offset_seconds;
   -- offset_seconds ควรเป็น 25200 และทั้งสองเวลาต้องตรงนาฬิกาจริง
   ```

## ข้อมูลเดิมและการเชื่อมต่ออื่น

- ค่า `TIMESTAMP` ใน MariaDB เป็น instant ที่ฐานข้อมูลแสดงผ่าน session UTC+7 ส่วน `DATE`, `DATETIME`, JSON และสตริงเวลาเป็นค่าที่ไม่มีเขตเวลากำกับ ค่าจาก session ใหม่และ API ของระบบถือเป็นเวลาไทย แต่ที่มาของข้อมูลเก่าอาจต่างกัน
- การแก้ครั้งนี้ **ไม่เลื่อนหรือเขียนทับข้อมูลเวลาเดิมโดยอัตโนมัติ** อย่าเพิ่ม/ลดเจ็ดชั่วโมงกับข้อมูลเก่าแบบยกชุด ผู้ดูแลควรสำรองข้อมูล ตรวจชนิดคอลัมน์ แหล่งที่มา และตรวจตัวอย่างกับเจ้าของข้อมูลก่อนพิจารณาแก้เฉพาะรายการ
- ระบบไม่ seed เช็กอินตัวอย่างใหม่ลงฐานข้อมูลจริงแล้ว แต่ไม่ลบรายการเก่าที่แยกจากข้อมูลจริงไม่ได้ หากเคยมีข้อมูลทดสอบเดิมต้องให้ผู้ดูแลตรวจและจัดการอย่างระมัดระวัง
- `generatedAt` ของ Office และ `serverTime` ของ `/api/clock` เป็น UTC ISO instant ส่วน `date`, `time`, เวลาในปฏิทิน และสตริงเวลาที่อ่านจาก MariaDB session เช่น Hermes `expiresAt` เป็นเวลาไทยตามสัญญา API ดู `docs/API-MANUAL.md` และ `docs/3D-OFFICE.md`
- โฟลเดอร์ `web/` เป็น dashboard scaffold แยกที่ Express ไม่ได้ใช้แทน Vanilla SPA หากเปิดทดลอง หน้า dashboard เปรียบเทียบวันครบกำหนดกับวันกรุงเทพและเทียบ `/api/clock` เช่นกัน; หากเทียบครั้งแรกไม่ได้จะแจ้งว่าใช้เวลาอุปกรณ์

## ทดสอบ

รัน `npm test` สำหรับชุดทดสอบทั่วไป หากมี MariaDB ทดสอบแยกบนเครื่องและผู้ใช้ทดสอบมีสิทธิ์สร้าง/ลบฐานข้อมูลชั่วคราว ให้ตั้ง `MNG_TEST_DB_ALLOW_CREATE=1` และ `MNG_TEST_DB_SOCKET` ตามขั้นตอนใน `docs/PROJECT-FLOW.md` ชุดทดสอบครอบคลุมวันข้ามปี/เที่ยงคืน หลาย timezone ของ process ปฏิทิน ลงเวลา การเชื่อมต่อ MariaDB และการหมดอายุ Hermes โดยไม่ใช้ฐานข้อมูล production
