# คู่มือปฏิบัติงาน Project Flow, AI และ Webhook

## ขอบเขตที่ทำได้จริง

- แท็บ **ติดตามงาน** อ่านสถานะจากงานที่เชื่อมกับแต่ละขั้นตอน เปลี่ยนสถานะและเปิดการ์ดงานจริงได้ สถานะที่แก้จะบันทึกในฐานข้อมูลงานเดิม
- แท็บ **AI & ส่งออก** สำหรับ Admin/Manager/Super Admin: สร้างร่างจากขั้นตอน ให้ AI ช่วยร่างถ้าตั้งค่าไว้ ตรวจและอนุมัติ แล้วกดยืนยันส่ง webhook ด้วยตนเอง มีประวัติผู้ดำเนินการและ `revision`
- AI ใช้ **Chat Completions API ที่เข้ากันได้กับ OpenAI** ตาม URL และโมเดลที่ผู้ดูแลตั้งในเซิร์ฟเวอร์ การเลือกชื่อโมเดลในบรีฟเป็นแผน ไม่ได้เปลี่ยนโมเดลที่เรียกจริง
- Webhook ส่ง JSON ที่ลงลายเซ็นไปยัง endpoint ขององค์กร เช่น workflow ที่องค์กรสร้างใน n8n **ยังต้องสร้างและทดสอบ workflow ฝั่งรับเอง** เพื่อเชื่อม LINE OA, Facebook, CRM, อีเมล หรือบริการอื่น ไม่มีตัวเชื่อมเฉพาะแพลตฟอร์มเหล่านั้นในชุดนี้
- การตอบ `2xx` จาก webhook หมายถึง **ผู้รับ webhook ตอบรับ** เท่านั้น ไม่ยืนยันว่าโพสต์สื่อ ส่งถึงลูกค้า ปิดการขาย หรือดำเนินการปลายทางสำเร็จ ต้องตรวจผลในระบบปลายทาง
- ไม่มีการส่งหรือรันเบื้องหลังอัตโนมัติ และไม่มีระบบรับ Lead หรือ Ticket จากภายนอกในชุดนี้ โหมดสาธิตไม่เรียกบริการจริง
- ปุ่ม `/api/ai/dispatch` และการตอบ @AI / สรุปพื้นฐานใน Chat เดิมเป็น **การจำลองหรือแม่แบบ** ไม่เรียกโมเดลจริง ส่วน AI จริงอยู่ใน Project Flow → **AI & ส่งออก**

## สิทธิ์ ความเป็นส่วนตัว และ Kill-switch

1. รายการส่งออก ประวัติและเนื้อหาอ่าน/เขียนได้เฉพาะ `manager`, `admin`, `super_admin` แต่ไม่แยกสิทธิ์รายโปรเจกต์ ผู้มีสิทธิ์เหล่านี้เห็นรายการทุกโปรเจกต์ที่ยังไม่เก็บเข้าคลัง
2. สมาชิกที่เข้าสู่ระบบดู Flow และติดตาม/อัปเดตงานในบอร์ดได้ตามสิทธิ์งานเดิม การเพิ่ม แก้ไข ลบ หรือพัก AI Agent และปุ่มพักทั้งทีมจำกัด Manager/Admin
3. การสร้างร่างด้วย AI จะส่ง **ชื่อโปรเจกต์ ชื่อและรายละเอียดขั้นตอน เป้าหมาย กลุ่มเป้าหมาย สิ่งส่งมอบ ข้อจำกัด เนื้อหาร่างที่บันทึกแล้ว (สูงสุด 4,000 ตัวอักษร) และคำสั่งที่ผู้ใช้ระบุ** ไปยังผู้ให้บริการ อาจมีค่าใช้จ่าย ต้องตรวจสิทธิ์และข้อมูลส่วนบุคคลก่อนยืนยัน
4. ต้องมี Agent อย่างน้อยหนึ่งตัวที่ไม่ถูกพัก หากขั้นตอนหรือบรีฟระบุ Agent ตัวนั้นต้องมีอยู่และไม่ถูกพักด้วย ปุ่ม **Master Kill-Switch** ใน AI Hub สั่งพัก Agent ที่มีอยู่ทุกตัว จึงบล็อกการเริ่มเรียก AI ใหม่จาก Flow แต่ไม่ใช่สวิตช์ส่วนกลางถาวร: หากเพิ่ม Agent ที่เปิดอยู่หรือเปิด Agent กลับ เงื่อนไขจะเปลี่ยนและอาจเรียก AI ได้อีก (Agent ที่ระบุในบรีฟ/ขั้นตอนยังต้องเปิดอยู่ด้วย) การพัก **ไม่ยกเลิกคำขอที่เริ่มไปแล้ว** และไม่หยุดการส่ง webhook ที่คนยืนยันเอง
5. รายการส่งออกอาจมีข้อมูลลูกค้าและถูกเก็บในฐานข้อมูลพร้อมประวัติ จำกัดการเข้าถึงและกำหนดระยะเก็บข้อมูลตามนโยบายองค์กร ห้ามใส่รหัสผ่าน API key หรือ token ลงในบรีฟ ร่าง หรือคู่มือ

## ตั้งค่าบริการ (ผู้ดูแลระบบ)

แก้ `server/.env` ที่มีอยู่ หรือกำหนด environment ผ่านตัวจัดการความลับของ Plesk/Passenger **อย่าเขียนทับค่าฐานข้อมูลเดิม และอย่า commit `.env`** ตัวอย่างชื่อค่า (ใช้ค่าจริงจากผู้ให้บริการขององค์กรเท่านั้น):

```dotenv
# URL เต็มของ Chat Completions ที่เข้ากันได้กับ OpenAI
FLOW_AI_URL=https://api.openai.com/v1/chat/completions
FLOW_AI_KEY=<ตั้งค่าความลับในเซิร์ฟเวอร์>
FLOW_AI_MODEL=<ชื่อโมเดลที่ endpoint รองรับ>

# ตัวรับที่องค์กรควบคุม เช่น workflow รับ webhook ของ n8n
FLOW_WEBHOOK_URL=https://<host-ขององค์กร>/<path>
FLOW_WEBHOOK_SECRET=<สุ่มความลับอย่างน้อย-32-ไบต์>
```

- ปล่อยว่างทั้งหมดได้ ฟีเจอร์ที่ไม่มีค่าจะไม่ทำงานและตอบ `503` URL ต้องเป็น HTTPS ไม่มี username/password, query string หรือ fragment และไม่ติดตาม redirect ตั้ง URL โดยผู้ดูแลระบบเท่านั้น; browser/API ไม่สามารถเลือก URL หรือ key ได้
- ใช้ secret ที่สุ่มอย่างน้อย 32 ไบต์ เช่นผลลัพธ์จาก `openssl rand -hex 32` ตั้งค่าเดียวกันในตัวรับอย่างปลอดภัย อย่าส่งค่าในแชตหรือ URL
- AI ส่ง `model`, `messages`, `max_tokens: 1200` รูปแบบ Chat Completions ผู้ให้บริการ/โมเดลที่ไม่รองรับรูปแบบนี้ต้องใช้ endpoint ที่เข้ากันได้ ไม่มีการสลับโมเดลตามชื่อในบรีฟ
- ตั้งค่าผ่าน server แล้วรีสตาร์ต Passenger ตามขั้นตอนของเครื่อง สถานะ “ตั้งค่าแล้ว” ตรวจเพียงรูปแบบค่า ไม่ได้ทดสอบสิทธิ์ API เครือข่าย โควตา หรือตัวรับจริง ควรทดลองด้วยข้อมูลทดสอบและบัญชีทดสอบก่อน
- ต้องมีสิทธิ์สร้างตาราง `erp_flow_actions`, `erp_flow_action_events` และเพิ่มคอลัมน์ที่ขาดตอนเริ่มระบบ สำรองฐานข้อมูลก่อน deploy ตรวจ log และ `/api/db/audit` ซึ่งตรวจการอ่าน/นับ 23 ตารางรวม auth DB แต่ไม่ตรวจทุกคอลัมน์ ควรตรวจ schema และทดสอบด้วยข้อมูลทดสอบด้วย หาก schema ไม่พร้อม หน้ารายการจะแจ้งข้อผิดพลาด ไม่ส่งข้อมูลแทน

## วิธีใช้งาน

1. สร้าง/บันทึกผัง แล้วกด **สร้างงานจากผัง** หากต้องการการ์ดงาน เปิด **ติดตามงาน** เพื่อดูสถานะรายโซนและเปลี่ยนสถานะ งานที่ย้ายโปรเจกต์หรือเก็บเข้าคลังจะขึ้นว่าไม่พบ และไม่ถูกสร้างใหม่โดยอัตโนมัติ
2. เปิด **AI & ส่งออก → สร้างร่าง** เลือกขั้นตอน ประเภท `media`, `sales` หรือ `support` ใส่ชื่อ ปลายทาง และเนื้อหา ปลายทางเป็นเพียงข้อความสำหรับ workflow ที่องค์กรควบคุม ไม่ใช่ URL ที่ ERP จะเรียก
3. ถ้าต้องการให้ AI ช่วย ให้บันทึกร่างก่อน กด **ช่วยร่างด้วย AI** ใส่คำสั่งและยืนยันสิทธิ์ส่งข้อมูล ผลที่ได้ยังเป็นร่างและต้องตรวจข้อเท็จจริงเอง
4. ผู้มีสิทธิ์ตรวจเนื้อหา ความยินยอม ปลายทาง และสิทธิ์สื่อ แล้วกด **ตรวจและอนุมัติ** การอนุมัติยังไม่ส่งออก ผู้อนุมัติอาจเป็นผู้สร้างได้ องค์กรที่ต้องการแยกหน้าที่ควรกำหนดนโยบายเพิ่มเติม
5. กด **ส่ง webhook** แล้วยืนยันอีกครั้ง สถานะ `Webhook รับแล้ว` เป็นเพียงการรับโดย webhook ตรวจผลจริงในระบบปลายทาง ประวัติมีผู้สร้าง ผู้อนุมัติ ผู้ส่ง และเหตุการณ์ประกอบ
6. ถ้าได้ **ต้องตรวจสอบผล** หรือการส่งค้าง ห้ามกดส่งซ้ำจนกว่าจะตรวจบันทึกปลายทาง สถานะค้างจากเซิร์ฟเวอร์หยุดจะให้บันทึกผลได้หลังอย่างน้อย 2 นาที เมื่อยืนยันว่าปลายทางไม่รับและบันทึกหลักฐาน ระบบคืนเป็นร่างที่แก้เนื้อหาไม่ได้ ต้องอนุมัติใหม่ก่อนส่งซ้ำ และใช้ `eventId` กับ payload เดิม หากต้องเปลี่ยนเนื้อหาให้สร้างรายการใหม่หลังจัดการผลเดิมแล้ว
7. ถ้าการเรียก AI ค้างเกิน 2 นาที ตรวจค่าใช้จ่าย/บันทึกผู้ให้บริการก่อนใช้ **บันทึกผลตรวจสอบ** เพื่อคืนร่าง การลองใหม่อาจมีค่าใช้จ่ายซ้ำ

ไม่มีการ retry อัตโนมัติ HTTP ที่ไม่ใช่ 2xx, timeout, การเชื่อมต่อขัดข้อง หรือ response ใหญ่เกินกำหนดถือเป็นผล **ไม่แน่นอน** เพราะปลายทางอาจประมวลผลไปแล้ว ประวัติและสถานะ `sending` ถูกบันทึกก่อนเรียก network หากบันทึกผลกลับฐานข้อมูลไม่สำเร็จ ให้ตรวจปลายทางและ reconcile หลังพ้นเวลารอ

## สัญญาการรับ Webhook

ทุกคำขอเป็น HTTPS `POST` JSON โดยมี header:

| Header | ความหมาย |
| --- | --- |
| `X-MNG-Event-ID` และ `Idempotency-Key` | UUID เดียวกับ `eventId` ใน body; คงเดิมทุกครั้งที่ตรวจแล้วอนุญาตส่งซ้ำ |
| `X-MNG-Timestamp` | Unix timestamp เป็นวินาทีของคำขอนั้น |
| `X-MNG-Signature` | `sha256=` ตามด้วย HMAC-SHA256 hex ของ `timestamp + '.' + raw body` |

ตัวอย่าง body (ข้อมูลตัวอย่างเท่านั้น):

```json
{
  "eventId": "00000000-0000-4000-8000-000000000001",
  "eventType": "mng.flow.action.approved",
  "kind": "support",
  "project": {"id":"p1", "name":"โปรเจกต์ตัวอย่าง"},
  "node": {"id":"support", "title":"ดูแลลูกค้า"},
  "action": {"id":"fa1", "title":"ตอบคำถาม", "destination":"ช่องทางที่กำหนดใน workflow", "content":"เนื้อหาที่ตรวจแล้ว"},
  "approval": {"userId":1, "name":"ผู้ตรวจ", "at":"2026-10-28 10:00:00"}
}
```

เวลาจากฐานข้อมูลใน `approval.at` เป็นสตริงตาม timezone ของเซิร์ฟเวอร์ฐานข้อมูล ไม่ใช่ UTC ที่มีตัวระบุ timezone ระบุเวลา/เขตเวลาใน workflow หากต้องอ้างอิงข้ามระบบ Payload ถูกแช่แข็งตั้งแต่ครั้งแรก จึงยังแสดงการอนุมัติครั้งแรกเมื่อส่งซ้ำ ส่วนการอนุมัติซ้ำอยู่ในประวัติ ERP

**ตัวรับต้องทำทั้งสามข้อ** ก่อนใช้กับบริการจริง:

1. ตรวจ HMAC จาก **raw bytes ก่อน parse JSON** ด้วย constant-time comparison และตรวจ timestamp ภายในช่วงที่กำหนด (เช่น 5 นาที) เชื่อมผ่าน TLS ที่เชื่อถือได้เท่านั้น
2. ตรวจ `eventId` ใน header/body ให้ตรงกัน และบันทึก `eventId` พร้อม hash ของ body กับการเข้าคิวงานใน transaction เดียวกัน หากซ้ำและ body เดิม ให้ตอบ `2xx` โดยไม่ทำงานซ้ำ หาก ID เดิมแต่ body ต่าง ให้ปฏิเสธ ควรมี unique constraint ที่ฐานข้อมูลฝั่งรับ การมี header เพียงอย่างเดียว **ไม่ป้องกันซ้ำ**
3. อนุญาตเฉพาะชนิด/ปลายทางที่องค์กรกำหนดใน workflow ตรวจสิทธิ์และความยินยอมก่อนเรียกผู้ให้บริการ และตอบ `2xx` หลังรับเข้าคิวถาวรเท่านั้น จัดการความล้มเหลวหลังรับในระบบปลายทางเอง

ตัวอย่างฟังก์ชันตรวจลายเซ็น Node.js (ต้องนำไปใช้ก่อน JSON parser; ไม่รวมฐานข้อมูล idempotency หรือการส่งต่อ):

```js
const crypto = require('node:crypto');
function verifyWebhook(rawBody, headers, secret) {
  const timestamp = String(headers['x-mng-timestamp'] || '');
  const signature = String(headers['x-mng-signature'] || '');
  if (!Buffer.isBuffer(rawBody) || Buffer.byteLength(secret || '', 'utf8') < 32) return false;
  if (!/^\d{10}$/.test(timestamp) || !/^sha256=[0-9a-f]{64}$/.test(signature)) return false;
  if (Math.abs(Math.floor(Date.now() / 1000) - Number(timestamp)) > 300) return false;
  const expected = crypto.createHmac('sha256', secret).update(timestamp + '.').update(rawBody).digest();
  const supplied = Buffer.from(signature.slice(7), 'hex');
  return supplied.length === expected.length && crypto.timingSafeEqual(supplied, expected);
}
```

## API สำหรับ Hermes และระบบอื่น

ต้องเข้าสู่ระบบด้วย session หรือ Hermes token และมีสิทธิ์ Manager/Admin ทุก endpoint ในตารางนี้ ส่ง `revision` ล่าสุดเป็นจำนวนเต็มและ `confirm: true` สำหรับคำสั่งที่มีผล; ใช้ `GET` ใหม่หลัง `409` ห้าม retry ทับอัตโนมัติ

| Method | Endpoint | รายละเอียด |
| --- | --- | --- |
| `GET` | `/api/flow/integrations` | สถานะการตั้งค่าและชื่อโมเดล ไม่คืน URL หรือ secret |
| `GET`, `POST` | `/api/projects/:id/flow/actions` | ดู 100 รายการล่าสุดหรือสร้างร่าง ส่ง `nodeId`, `kind`, `title`, `destination`, `content`; แนะนำ `eventId` UUID v4 เดิมเมื่อ retry การสร้าง |
| `GET`, `PATCH` | `/api/projects/:id/flow/actions/:actionId` | อ่านร่าง/ประวัติ หรือแก้ร่างที่ยังไม่เคยส่ง (`revision`) |
| `POST` | `.../:actionId/generate` | `{revision, confirm:true, instruction}`; ส่งข้อมูลไป AI จริงและบันทึกร่างใหม่ |
| `POST` | `.../:actionId/approve`, `.../return-draft`, `.../cancel` | อนุมัติ ถอนอนุมัติ หรือยกเลิก โดยไม่ส่ง webhook |
| `POST` | `.../:actionId/send` | ส่งรายการที่อนุมัติแล้ว; ดู `accepted` และ `action.status` แยกจาก HTTP status |
| `POST` | `.../:actionId/reconcile` | `{revision, confirm:true, resolution:'accepted'|'not_accepted'|'reset_generation', note:'หลักฐานอย่างน้อย 10 ตัวอักษร'}` ตามสถานะและเวลาที่อนุญาต |

ตัวอย่างอ่านรายการด้วย Hermes client ซึ่งหมุน token ตามปกติ:

```bash
python3 skills/mng-erp/scripts/mng_erp_client.py request GET /api/projects/p1/flow/actions
```
